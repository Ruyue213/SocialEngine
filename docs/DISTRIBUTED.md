# 多机分布式扩展设计（方案文档）

单机引擎容量受内存限制（千万级节点）。本方案给出上亿级节点的分片扩展设计，暂不实现。

## 1. 分片策略

- **按节点 ID 一致性哈希分片**：`shard = consistent_hash(user_id)`，每片持有其节点
  的完整邻接（本机引擎的"分片桶"概念的自然延伸）
- **边的归属**：边 (u,v) 冗余存储在 u 片和 v 片（每个端点各存一份），任一单点查询
  只访问一个分片
- 一致性哈希 + 虚拟节点：扩缩容时仅迁移相邻分片的数据（迁移量 O(数据量/分片数)）

## 2. 查询路由

| 查询 | 路由 |
|---|---|
| 二度好友 sd(u) | 单分片：u 所在片 |
| 共同好友 cf(u,v) | 两片：u 片 ∩ v 片（或取度数小者的分片，仅传 u 的邻接过去） |
| 最短路径 dist(u,v) | 全局：双向 BFS 跨片，每跳一次 RPC |

## 3. 跨片 BFS

双向 BFS 的每层扩展是"批量邻居查询"：把 frontier 按目标分片分组，各片并行
`BatchNeighbors(ids)` RPC 返回邻接（一次 RPC 收一层），层数 = 图直径（社交图 ~6）
→ 每查询 6 轮 RPC 扇出。热点 hub 由分片内缓存 + 容忍窗口吸收。

## 4. 一致性与持久化

- 每片独立 WAL + 快照（本机机制复用）
- 跨片更新（add/delete 一条边涉及两片）：两阶段提交或"先写 u 片、异步补 v 片 +
  幂等重放"（边数据天然幂等，最终一致可接受）
- 版本失效、延迟双删机制不变（Redis 集群按 key 分槽）

## 5. 热点与容量

- **Hub 节点**（大V粉丝链）：邻接可达数万条，单分片可承载；读取走 COW 快照；
  极端热点可二级索引（边列表按创建时间分块 + 增量拉取）
- **热点分片**：读多写少天然适合加只读副本；副本间用 WAL 流复制
- 分片规模：每片 500 万节点/1 亿边，上亿节点 ≈ 20-50 片

## 6. 面试可讲要点

1. 为什么选一致性哈希而不是取模分片（扩缩容迁移量）
2. 为什么边双端存储（单点查询零跨片）与空间代价（2x 边存储）的权衡
3. 跨片 BFS 的 RPC 扇出模型与跳数上界（社交图直径小）
4. 幂等重放如何让跨片更新不需要分布式事务
