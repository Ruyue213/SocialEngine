# 设计文档：架构与取舍

## 1. 问题定义

社交好友关系链 = 超大规模稀疏无向图。两类核心需求：
- 高频只读查询：共同好友（交集）、二度好友（BFS≤2）、最短路径（双向BFS）
- 低频增量写入：加/删好友，需要实时可见

约束：百万级节点、每秒上万查询、内存受限（单机）、延迟敏感。

## 2. 存储设计

### 2.1 为什么是邻接表而不是邻接矩阵
社交图稀疏（平均度 20~200），邻接矩阵 99% 空间浪费，O(N²) 不可行。

### 2.2 为什么不用 std::list / 现成图数据库
- 通用图数据库（Neo4j 等）：功能冗余、内存开销大，与垂直查询场景不匹配
- 原生链表：每边一次堆分配（16~24B/边 + 分配器开销）、随机访存导致缓存命中率极低、
  增删导致内存碎片化
- 本项目场景极窄（只有两种遍历形态），值得为它定制存储布局

### 2.3 分层邻接结构
每个节点的好友集合 = N 块定长压缩块（1KB，存"稳定历史"）+ 1 块尾部动态缓冲（存新边）：

```
┌─块0─┐ ┌─块1─┐        ┌─尾部─┐
│24B头│→│24B头│→ ... → │ cap  │
│varint│ │varint│       │ len  │   ← 元数据内嵌于不可变 AdjacencyData
│差值  │ │差值  │       │ 新边 │
│…     │ │…     │       │ 追加 │
│位图  │ │位图  │       └──────┘
└──────┘ └──────┘
```

- **差值压缩**：好友 ID 排序后存 varint 差值（社交 ID 局部连续，压缩率 ~3-5x）
- **O(1) 均摊增边**：追加到尾部缓冲；写满才触发低频重排序+压缩（O(K)，摊还 O(1)）
- **O(1) 删边**：尾部写哨兵值、块内位图置位（懒删除），查询遍历时跳过
- **空洞整理**：删除占比 > 40% 触发后台低优先级线程异步重压缩（不阻塞查询）

### 2.4 Slab 内存池
4KB 页切 64B/128B/.../4096 七档插槽。普通节点起步 64B，超大节点（hub）才分配完整块。
侵入式空闲链表复用空闲块前 8 字节存 next；后 8 字节写 `0xDEADBEEFCAFEBABE` 魔数哨兵，
剩余字节填充 0xCD，分配时校验魔数+指针合法性拦截越界篡改（本项目曾用此定位野指针
覆盖空闲链表的随机段错误）。

## 3. 并发设计

### 3.1 哈希分片 + 读写锁（写侧）
节点按 splitmix64(userID) % K 散列到 K 桶，每桶一把 `shared_mutex`：
- 写者（增删边/重建）独占写锁，且多锁时严格按桶 ID 升序加锁（杜绝交叉死锁）
- 哈希均匀时锁竞争降低到 1/K

### 3.2 COW 邻接 + 全局 Epoch（读侧，核心亮点）
**问题**：读锁与写锁互斥，BFS 遍历热点节点时读锁阻塞写者，写者重建时读者无法进入。
**方案**：读路径完全无锁，用"写时复制 + 延迟回收"保证安全：

1. **单指针原子发布**：每个节点的 `{head链, tail, cap, len, deleted}` 打包进一个
   `AdjacencyData`，由单个原子指针发布。读者一次 acquire-load 拿到全节点的一致快照，
   不存在"读到新 len 旧数据"的撕裂窗口
2. **写时复制**：有活跃读者时，写者克隆尾部/块链路径后再修改（路径复制，持久化数据
   结构风格），修改完成后原子 swap + 旧结构挂 retire 列表
3. **全局 Epoch 回收**（RCU 思想）：读者进入查询时 Pin 一个 ticket（记录当前全局
   epoch）；写者 retire 的对象挂在 epoch 分桶列表；维护线程 Sweep 时只有所有活跃
   读者都越过某 epoch 才释放对应桶。64 桶 + 无活跃读者时 epoch 跳跃推进，回收器
   始终追得上 retire 速率
4. **内存序论证**：Pin 与 Retire 使用 seq_cst 的 epoch 读写建立 happens-before 链，
   保证"读者 Pin 在 E' > 写者 retire 在 E"时必然读到新指针（coherence + S 序）

**语义**：单节点邻接读取原子一致；跨节点遍历（BFS）是"每个节点在其各自时刻的
一致视图"的近似快照——对社交查询（容忍毫秒级弱一致）是合理的正确性/性能折中。

### 3.3 为什么不用完整 RCU
RCU 要求读者全程无锁且写者等待所有读者退出（grace period）——写者可能被长查询
阻塞；Epoch 回收让写者立即返回（retire 异步释放），更贴合"读多写少但写不阻塞"的需求。

## 4. 查询执行

- **双向 BFS**：两侧交替扩展小前沿；每侧维护 Epoch 距离数组精确求最短路
- **Epoch 时间戳标记**：visited 数组用 uint32 批次号，查询间不 memset（高并发下
  memset 会打满内存总线带宽）
- **每工作线程私有 visited/前沿/scratch**：无锁、缓存友好
- **共同好友**：双有序数组双指针交集，`__restrict__` 解除指针别名障碍激活向量化
- **N+1 绑核线程池**：防上下文切换与跨核迁移丢失 L1/L2

## 5. 缓存一致性（Redis）

- 旁路缓存：读命中直返，未命中回源计算+异步回填（TTL + allkeys-lru 淘汰）
- 版本失效：每次更新 INCR 节点版本号；缓存值内嵌写入时版本，读取时 Lua 脚本校验
- **延迟双删**：更新后立即异步 DEL + 最小堆定时器 5ms 后二次删除（兜底并发脏读）
- **容忍窗口**：更新同时 PSETEX 一个 100ms 脏标记键；窗口内版本不匹配的旧值仍可
  命中（可接受毫秒级脏读），窗口到期自动恢复严格一致
- **幂等**：更新接口携带 dedup_key，Redis SETNX 原子抢占去重，重复投递不重复生效
- **保护**：读队列优先+写可丢（缓存写不阻塞查询）；连接失败熔断回退直连计算

## 6. 持久化（WAL）

- 固定 33B 记录（magic+op+seq+u+v+CRC32）追加日志；LSN 单调递增
- 两档 fsync：组提交（后台批量 write+fdatasync，高吞吐）/ 逐条同步（强一致）
- 定期快照 + WAL 轮转；恢复 = 加载快照 + 重放 LSN 之后的记录
- **幂等重放**：AddEdge/RemoveEdge 天然幂等，快照导出期间的并发更新在重放时被
  去重检查吸收——快照不需要严格的一致性点
- 尾部截断（torn write）容忍：CRC 校验失败即停止重放，坏记录被丢弃
- 批量加载（建图）绕过 WAL，完成后落一次快照（避免 fsync 风暴）

## 7. 网络层与过载保护

- Multi-Reactor：主 Reactor accept + N 子 Reactor epoll/kqueue 边缘触发；响应跨线程
  按请求序号投递保证 HTTP 管道化顺序
- Load Shedding：任务队列容量校验 + try_lock（锁竞争即视为过载）→ 立即 503 +
  Retry-After，客户端指数退避
- 优雅停机：停 accept → drain 在飞请求 → 刷 WAL → 关连接

## 8. 已知局限与后续方向

- 单机内存上限 ~千万节点；多机分片方案见 `docs/DISTRIBUTED.md`
- 快照读是节点级一致（非全图瞬时快照）；需要更强语义可加全局事务层
- SIMD 加速交集（AVX2 一次比对 8 个 ID）、BFS 算子下沉异构计算单元（NPU）
- 指标注册表为全局互斥（~3% 开销），可改分片
